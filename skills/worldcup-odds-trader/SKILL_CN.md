## 0. 核心目标

本 Skill 用于足球赛事的盘口分析、模拟投注、历史复盘、V3/V4 日更、Excel 历史台账更新、HTML 生成及 GitHub Pages 发布。

核心原则：

1. 先核对基本面拉力，再做欧赔去水，再判断亚盘真实意图，最后结合交易所/Polymarket 反向情绪和可执行价格决定是否下注。
2. `胜负概率`、`让球价值`、`盘口意图`、`可执行价格`必须分开，不得把其中一项直接当作另一项。
3. 证据优先于猜测，准确性优先于自动化，增量更新优先于全量重建。
4. 缺少关键数据时必须显示“待核/缺失/仅模拟”，不能把缺失数据转换为 0、不能编造盘口、赔率、资金流或历史胜率。
5. V3 与 V4 是两套独立版本。V3 为生产版本，V4 为 Shadow/研究版本；V4 不能覆盖 V3，也不能把 V4 结果混入 V3 台账。

## 2. 每日严格执行顺序

每天更新必须按以下顺序执行：

1. 锁定 `list_date`、北京时间、覆盖赛事范围和开赛截止时间。
2. 备份前一版本 HTML、JSON、CSV、Excel 和运行日志。
3. 先结算上一交易日：补充比分、状态、红/半红/走/半黑/黑、盈亏和 ROI；结算采用赛前冻结名单，不能用赛后重新计算的筛选结果。
4. 构建唯一的 Titan007 共享数据快照。
5. 先运行 V3，确认 V3 冻结名单、赛事数量和历史统计正常。
6. 再运行 V4，V4 只读取同一个共享数据快照。
7. 更新 V3/V4 Excel 至目标日期，保持原文件格式不变。
8. 用 Excel 重新计算每场比赛的历史统计、胜率、PnL 和 ROI。
9. 生成 V3/V4 HTML、JSON、CSV、Markdown 审计文件。
10. 校验筛选边界、冻结名单、行数、日期、字段、HTML 列和 V3/V4 分离。
11. 发布到 GitHub Pages，随后直接检查线上 HTML 和 JSON。
12. 只有本地、Excel、发布目录和线上页面均通过校验，才可以报告“更新成功”。

### 每日历史统计的强制数据顺序

每日 HTML 的高/低胜率、近期样本、PnL 和 ROI 必须严格按以下顺序动态生成：

1. 先把当天 `list_date` 的完整赛事快照追加到 V3/V4 各自 Excel 台账；重复运行不得重复追加。
2. 再把上一 `list_date` 的冻结赛果回写到两份 Excel，包括比分、结算状态、红/半红/走/半黑/黑、盈亏、结果来源和更新时间。
3. Excel 校验通过后，只从对应版本 Excel 读取同名赛事历史，计算近期样本、有效胜率、PnL 和 ROI；JSON/CSV 若未回写 Excel，不得作为历史统计依据。
4. 最后用上述 Excel 统计结果生成 HTML 并发布。Excel 回写或校验失败时，必须阻断高低胜率分类和发布，不能用空值或旧统计替代。

## 3. 高低胜率筛选规则

用户当前确定的阈值：

- 高胜率：有效胜率 `>=55%`。
- 低胜率：有效胜率 `<45%`。
- 中间区间：`45% <= 有效胜率 <55%`，既不是高胜率，也不是低胜率。
- 低胜率绝不能按“40%以下”或“空值转 0”处理，当前统一按 `<45%`。
- 历史样本必须 `historical_settled_sample > 8` 才能触发高/低胜率标签。
- 空值、NaN、缺少历史数据时显示“历史待核/无样本”，不得显示为 0% 低胜率。
- 港联杯、杯赛、友谊赛等必须按精确规范化后的赛事名称匹配，不能因为字符串相似而并入错误的历史样本。
- 当天比赛不能进入当天的历史样本；历史截止时间严格早于当前 `list_date`。

有效胜率公式：

```text
有效胜率 = (红 + 0.5 × 半红)
          / (红 + 0.5 × 半红 + 黑 + 0.5 × 半黑)
```

走盘不进入有效胜率分母，但计入已结算样本数。

## 4. 每场比赛必须显示的历史统计和 ROI

无论是否属于高/低胜率，HTML 每场比赛都要写入动态字段：

- 历史已结算样本数
- 红数
- 半红数
- 走盘数
- 半黑数
- 黑数
- 有效胜率
- 平注 1U 盈亏 `pnl_1u`
- `ROI`
- 历史来源版本：V3 或 V4
- 历史匹配的精确赛事名称
- 历史截止日期

ROI 公式：

```text
ROI = pnl_1u / historical_settled_sample
```

无样本或结算输入不完整时，ROI 保持空值或“待核”，不能假造 0%。

HTML 展示要求：

- V3 至少在每场比赛详情/统计区域显示上述字段。
- V4 在赛事表中单独增加“历史统计 / ROI”列。
- 触发高胜率或低胜率时，显示样本数、有效胜率和 ROI；未触发但有历史样本时，也要显示正常统计；无样本时显示“无样本/待核”。
- 每场比赛都必须写入动态胜率和 ROI，不得只给触发行写入。

## 5. 冻结名单与结算规则

- `list_date` 的赛事名单一旦锁定，不得因为接口缺失、状态改变或筛选重算而缩表。
- 赛前冻结的可投/半仓可投决策是结算分母的唯一依据。
- 开赛后只允许追加比分、比赛状态、红/黑/走、盈亏、比分来源、结算时间和复盘备注。
- 不得因为比赛已开始、已结束、当前赔率变化或赛后重新计算变成“不投”，从而删除原先的冻结可投记录。
- 若冻结名单缺失，必须明确写出“冻结可投底稿缺失，不能声称可投回顾完整”，可从时间戳快照重建，但要标记“重建冻结名单”。
- 每次结算前先输出：赛前冻结可投数、找到数、已结算数、进行中/待核数、取消/延期数、纳入分母数、排除原因。
- 出现类似“103 条变成 43 条”的缩表，默认视为台账语义错误，先修复数据源，不能直接当成真实结果。

## 6. 盘口分析的五块链条

每场可读盘口赛事按以下顺序处理：

1. **基本面拉力**：实力、主客场、赛程、动机、淘汰/晋级形势、阵容、体能、天气和场地。
2. **欧赔去水**：原始 1X2、返还率、去水概率、市场概率与足球基本面概率的差异。
3. **亚盘真实意图**：开盘、即时盘、水位变化、升降盘、拉力方向，分类为阻上、诱上、阻下、诱下、降温强队或无效噪音。
4. **交易所/Polymarket 反向情绪**：价格、成交量、流动性、价量变化和市场拥挤方向。
5. **最终决策**：主盘口、替代盘口、可执行价格、止损线、正 EV 门槛、Kelly 和动作。

盘口观点不等于可下注：必须进一步检查具体市场、真实可成交价、价差、流动性、结算口径和最大入场价。

## 10. 每日提速后的推荐流程

### A. 正常全量更新：每天只做一次

```powershell
python D:\codex\run_football_update.py --list-date YYYY-MM-DD
```

这一步完成抓取、共享快照、V3、V4、Excel、历史统计、HTML、GitHub 发布和最终校验。

### B. 接口或发布失败后的快速重跑

如果原始赔率快照已经成功，只是 HTML、Excel 校验、发布或页面检查失败，不要重新抓取 Titan：

```powershell
python D:\codex\run_football_update.py --list-date YYYY-MM-DD --no-refresh
```

该模式复用最近一次本地原始快照，避免重复访问接口。重跑时必须在日志中显示复用的快照时间，并把未重新刷新赔率的字段标记为“沿用快照”。

### C. 只做当前日期/目标窗口

脚本支持 `--current` 时，仅在明确需要当前窗口时使用；不要因为网页显示异常就重复全量抓取全部赛事。当天名单仍须保持原始 roster 不缩表。

### D. 不要重复做的事情

- 不要在一次完整刷新失败后连续多次全量重跑。
- 不要在 GitHub 推送失败时重新抓取赔率；先复用本地产物重试发布。
- 不要为了检查浏览器页面而重复运行 V3/V4。
- 不要每次页面样式问题都重新构建 6000+ 历史卡片；先检查生成文件、路径和缓存参数。
- 不要重复上传大 HTML 文件；优先使用已配置好的 Git 方式发布。

### E. 当前已具备的提速点

- `--no-refresh` 已用于复用最新本地 raw snapshot。
- 浏览器 fallback 默认关闭，避免接口失败时进入慢速浏览器流程。
- V3/V4 使用共享 Titan 数据层，避免重复取同一事实。
- V3 先运行、V4 后运行，保持版本隔离和可审计性。
- 发布前统一做一次校验，避免“反复打开页面—反复重跑”的循环。

### F. 下一步安全优化建议

当前抓取器的并发数为 3，且请求有全局节流。下一步可把并发数改成环境变量控制，先在 6 个 worker 的小规模测试上观察接口错误率，再决定是否提高到 8；不能直接无限提高，避免 Titan 限流或返回不完整。

建议顺序：

1. 先记录 3 worker 的单次耗时、接口成功率和缺失率。
2. 试运行 6 worker，保持相同 list_date，比较耗时和数据完整性。
3. 只有接口成功率、赛事数、赔率字段和校验结果都不下降，才保留更高并发。
4. 如果失败，自动退回 3 worker，不能因为提速牺牲数据完整性。

V3 和 V4 本身仍应顺序运行；可并行的只包括发布后的只读校验，例如 JSON schema、Excel 格式校验、静态 HTML 字段检查和线上 URL 检查。

## 12. 结算、盈亏和 ROI

- 每场赛果必须按原先冻结的选择和盘口结算。
- 红、半红、走、半黑、黑必须区分。
- 平注 1U 盈亏使用原下注方向、原盘口和赛前水位。
- “墨西哥这场全红、日本两场全黑”等人工纠错，必须回到原始冻结方向、盘口、赛果逐场核对后修正，不能只改汇总数字。
- 结算统计按版本、赛事、市场类型、盘口区间、意图标签和日期拆分。
- V4 Shadow 的表现必须标记为研究/模拟表现，不能表述成真实投注盈利。
- 正式汇总前必须核对每场状态，不能把未赛、取消或延期记为黑，也不能把缺少赛果记为红。

## 13. 日报必须包含的内容

1. 日期、时区、覆盖赛事和名单数量。
2. 昨日冻结可投名单的结算、盈亏、ROI 和分母对账。
3. V3/V4 独立的历史高低胜率触发结果；无触发时明确写“无触发”。
4. 每场比赛的动态历史统计、胜率、ROI、盘口和决策状态。
5. 正式可投、半仓可投、不投、仅模拟和待核赛事分组。
6. 数据缺口、接口异常、Excel 校验结果和 GitHub 发布结果。
7. 如有错误，给出“保留规则 / 修正规则 / 新增规则”，不要为单场结果过拟合。

- 不得在 Excel 日期落后、格式校验失败、roster 缩表、决策漂移或 GitHub 推送失败时声称更新完成。
- 不得为了追求速度绕过共享快照、Excel 更新、历史/ROI 计算和线上验证。

## 16. 完成判定

一次日更只有同时满足以下条件，才能报告“完成”：

```text
接口快照成功
→ roster 未缩表
→ V3 成功
→ V4 成功且未覆盖 V3
→ Excel 更新到目标日期且格式通过
→ 每场历史统计及 ROI 已写入
→ 高 >=55%、低 <45%、中间区间不误筛
→ 结算分母来自冻结名单
→ HTML/JSON/CSV/MD 产物齐全
→ GitHub push 成功
→ 线上 HTML 与 JSON 验证通过
```

任何一环失败，都要报告具体失败环节和可复用的本地产物，不得用“页面看起来更新了”代替完整验证。
